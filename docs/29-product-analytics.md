# 29. Продуктовая аналитика: где люди застревают

> **Кратко:** Своя аналитика на Cloudflare (Workers Analytics Engine). Видим воронки, где люди уходят, и ошибки. Смотрим в админ Mini App и сразу исправляем.

## Цель (решение владельца)

- Понимать, **как люди пользуются Rida** и **где застревают**.
- Сразу видеть проблему и сразу исправлять.

## Технология

- Cloudflare Workers Analytics Engine (бесплатно до 100 000 событий в день).
- Mini App и боты отправляют события в backend одним пакетом (экономим запросы).
- Своя аналитика, без внешних сервисов (`03`).

## Какие события пишем

| Группа | События (проверено в G12) |
|---|---|
| Экраны | `screen_open` (Mini App, экран) |
| Шаги | `registration_step` (consent, about, phone, done; G34), `driver_application_step`, `trip_step`, `booking_step`, `way_step` (поиск списками: opened, from, to, done; G26) |
| Действия | `trip_search`, `trip_open`, `chat_open`, `chat_first_message`, `wallet_open`, `route_subscribed`, `subscriptions_open`, `review_sent`, `complaint_sent`, `complaint_decided`, `favorite_driver`, `return_trip_created`, `driver_trip_shared`, `driver_trip_story` |
| Ошибки | `client_error` (экран упал: код `render`, `uncaught` или `rejection`, класс ошибки, текст без цифр и знаков, экран, приложение Telegram и его версия, G52 `112`), `api_error` (код ответа API и последний открытый экран, G12) |
| Бот (G12) | `bot_command` (id команды), `bot_button` (вид кнопки, без id) |
| Сервер | `driver_approved` |
| Близкие (`43`) | `trip_shared`, `share_opened`, `share_follow`, `share_join`, `boarded`, `arrived` |

- Каждое событие: время, Mini App, экран, версия, ID сессии (одно открытие Mini App).
- **Без личных данных:** без имени, телефона, текста чата, точных координат.
  Схема принимает только id; лишние поля отбрасывает (тест в `packages/contracts`).
- Обычные ответы API не считаются ошибкой: `users.not_registered`, `drivers.not_found`.
- **`flow_abandoned` не пишем (решение G12):** уход виден в воронках по шагам,
  отдельное событие только тратит лимит.
- Аналитика описывается в «Maxfiylik siyosati» (G14).

## Воронки (где люди уходят)

1. **Попутчик:** открыл → искал → открыл поездку → запросил бронь
   → написал в чат → бронь подтверждена → поездка состоялась.
2. **Водитель:** открыл → начал заявку → отправил на модерацию
   → одобрен → создал поездку → подтвердил бронь.
3. **Создание поездки** по шагам: откуда → куда → когда → места → цена → готово.

На каждом шаге видно, сколько людей ушло. Большой уход = место, где застревают.

## Дашборд и сигналы

- Раздел «Statistika» в админ Mini App и сигналы в админ-бот: `56-analytics-dashboard.md`.

## Как устроено

- Схема: `packages/contracts/src/analytics.ts`. Экраны и коды: только id вида `home`, `my_trips`.
- Клиент: `createAnalyticsClient` (`packages/api-client`): пакет до 50 событий,
  отправка через 5 секунд или когда Mini App скрыт. Ошибка сети не ломает приложение.
- Backend: модуль `analytics`, `POST /analytics`. Порт `AnalyticsSink`: в проде
  Analytics Engine (привязка `ANALYTICS`), локально фейк в памяти.

## Объём событий (расчёт G12)

| Что | Значение |
|---|---|
| Реальные тесты (30 дней) | водитель 12 событий за открытие, попутчик 8 |
| Берём с запасом | 12 событий за открытие, 2 открытия в день |
| 2 000 активных людей | 2 000 × 2 × 12 = 48 000 событий |
| Боты (`bot_command`, `bot_button`) | около 2 на человека: 4 000 |
| **Итого в день** | **около 52 000 из 100 000: запас почти 50%** |

- Лимит будет близко при 4 открытиях в день на человека. Тогда: убрать `screen_open`
  у экранов без воронки (самое частое событие).
- Запросы к Analytics Engine (лимит 10 000 в день): дашборд хранит ответ 10 минут,
  сигналы проверяются раз в час. Меньше 1 000 запросов в день.

## Правила

- События описаны в одном месте (`packages/contracts`), одинаково во всех
  Mini App. Названия событий на английском.
- Писать только нужные события (лимит 100 000 в день).
- Сбор событий с недели 1, дашборд сделан в G12 (неделя 10, `27-launch-roadmap.md`).
