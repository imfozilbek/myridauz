# 49. Уроки: продолжение журнала (№21 и дальше)

> **Кратко:** Уроки №21 и дальше. `44` заполнен до лимита 150 строк. Правила журнала и короткая таблица всех уроков: `26-lessons-learned.md`.

### №21. Мок API на скриншотах вёл себя не как сервер

- **Что случилось:** на первых скриншотах выбора места (G05) регионы шли по коду
  СОАТО, а не по порядку `14` (Toshkent первым). Районы шли не по алфавиту.
- **Причина:** сервер сортирует справочник в SQL, а мок e2e отдавал файл seed как есть.
  Скриншоты показали поведение мока, а не продукта.
- **Следствие:** ошибку нашли при проверке скриншотов по «Планке качества» (урок №17),
  до показа владельцу. Потеряли один круг снимков.
- **Урок:** мок API повторяет правила сервера, которые видны человеку: порядок,
  фильтры, ошибки. Если правило есть только в SQL, мок делает то же самое, а тест сервера его проверяет.

### №22. Коммит в ветку PR после того, как владелец её слил

- **Что случилось:** в ветку PR #11 добавлен второй коммит (инструкция для GitHub Mobile).
  Владелец слил PR раньше, чем коммит дошёл до GitHub. Коммит не попал в `main`,
  а ветка снова появилась на GitHub после удаления.
- **Причина:** PR уже ждал слияния владельцем, а Claude продолжил пушить в его ветку.
- **Следствие:** ещё один PR (#12) и лишняя ветка, которую пришлось удалять вручную.
- **Урок:** PR, который ждёт слияния, больше не меняем. Новая правка: новая ветка от
  свежего `main` и новый PR.
- **Повтор 30.09 (G16, PR #46):** два коммита про ролик ушли в ветку после просьбы «слейте».
  Перенесены в PR #47. Правило: после сообщения владельцу «слейте PR» новые правки только в новый PR.

### №23. Пуш ушёл, хотя барьер качества упал

- **Что случилось:** в `docs/50` диапазон «1 … 2» был записан через среднее тире. `check:text` упал,
  но коммит всё равно ушёл в ветку PR #14.
- **Причина:** команда была цепочкой `pnpm check | grep … && git commit && git push`.
  Код выхода брался от `grep` (он нашёл строку «Tests»), а не от `pnpm check`.
  Тире появилось по привычке при записи диапазона чисел.
- **Следствие:** в ветке PR был коммит с красным барьером; исправлен следующим коммитом.
- **Урок:** пуш только после `pnpm check` с кодом выхода 0, отдельной командой.
  Диапазоны пишем словами: «1 и 2», «от 1 до 7», без тире.

### №24. Даты и суммы по-английски в браузере

- **Что случилось:** на скриншотах G07 сумма «90,000 soʻm» и дата «M09 30» вместо «90 000» и «30-sentabr».
- **Причина:** Chromium говорит, что знает `uz-Latn`, но данных для узбекского у него нет.
  Node форматировал верно, поэтому unit тесты были зелёными.
- **Следствие:** так же выглядело бы в части webview Telegram. Нашли до показа владельцу.
- **Урок:** названия месяцев и дней и разделитель тысяч берём из файла языка (`docs/13`),
  а из `Intl` только цифры. Вид текста проверяем на скриншотах из браузера, не только в Node.

### №25. Убрал регион из маршрута, чтобы строка стала короче

- **Что случилось:** в G07 строки маршрута переносились. Чтобы строка влезла, Claude оставил только район: «Chilonzor → Samarqand shahri».
- **Причина:** решали ширину экрана, а не задачу человека: понять, куда он едет.
- **Следствие:** владелец попросил вернуть два уровня; экраны переделаны (G07+).
- **Урок:** не убирать то, что помогает ориентироваться. Длинный текст решаем раскладкой (две строки, `RouteView`), а не сокращением.

### №26. Сказал о проде то, чего не проверил

- **Что случилось:** Claude написал владельцу: «водитель уже одобрен». Владелец открыл Mini App и увидел «Ariza tekshirilmoqda».
- **Причина:** состояние прода взято из памяти разговора, а не из проверки.
- **Следствие:** владелец потратил время на проверку, которая не могла пройти.
- **Урок:** о данных в проде говорить только после проверки или со словами «не проверял». Шаги проверки для владельца начинать с условий (например, «одобрите свою заявку»).

### №27. Номер машины и ссылка на карту сломались только в браузере

- **Что случилось:** в G08 unit тесты были зелёными, но на скриншоте госномер обрезался («BC» под «UZ»), подпись «Davlat raqami» пропала, а «Uchrashuv joyi» выглядела как синяя веб-ссылка.
- **Причина:** номер крупного размера поставили в узкую ячейку; ссылку `<a>` оформил браузер, а не Telegram.
- **Следствие:** нашли при своём просмотре скриншотов, до показа владельцу. Номер стал компактным (`PlateView small`), карта открывается через `openLink` Telegram.
- **Урок:** каждый новый экран смотреть на своём скриншоте до показа. Внешние ссылки открывать через Telegram SDK, а не тегом `<a>` (`docs/21`).

### №28. Водители, одобренные до G08, остались без бонуса

- **Что случилось:** бонус 500 000 начислялся только в момент одобрения. Водители, одобренные раньше (в G06 и G07), после деплоя G08 имели пустой кошелёк и не видны в «Hamyonlar».
- **Причина:** новое правило написали только для новых событий и не подумали о людях, которые уже есть в базе.
- **Следствие:** нашли при проверке прода сразу после деплоя, до проверки владельцем. Исправлено Cron-задачей: одобренный водитель с пустым кошельком получает бонус 1.
- **Урок:** у каждой новой функции спрашивать: «что будет с людьми и данными, которые уже есть в проде?» Переход для старых данных делать в той же цели.

### №29. Звонок не соединялся: запрос к Realtime не проверили на настоящем сервере

- **Что случилось:** в G13 владелец ответил на звонок, но увидел «Ulanib boʻlmadi». Сервер отвечал `calls.unavailable`.
- **Причина:** backend создавал сессию Realtime с пустым телом `{}`, а Realtime принимает только запрос без тела. Тесты шли с поддельным Realtime, который принимал всё. Второе: голос собеседника забирали до того, как его сторона соединилась.
- **Следствие:** первая проверка на телефонах не прошла, нужен ещё один деплой.
- **Урок:** каждый запрос к внешнему API до деплоя проверять один раз на настоящем сервере (тестовое приложение или ключ), а не только на подделке. Порядок шагов внешнего сервиса брать из его документации и проверять вживую.

### №30. Проверка бренда приняла узбекские слова за имя «Rida»

- **Что случилось:** в G14 `check:text` упал на `legal.json`: «tashqa**rida**» и «serverla**rida**».
- **Причина:** проверка ищет имя бренда внутри слова. В узбекском окончание места «-rida» очень частое.
- **Следствие:** две фразы оферты и политики переписаны («chetlab oʻtib», «boshqa davlatlarda»). Правило не ослаблено: оно ловит и «Ridadan».
- **Урок:** узбекский текст сразу проверять `node scripts/check-text.mjs`. Слова на «-rida» заменять синонимом или другим порядком слов.

### №31. Два скрипта взяли один и тот же атрибут

- **Что случилось:** счёт цифр в блоке «Rida raqamlarda» искал `[data-count]`. Этот атрибут уже был у счётчика мест в карточке маршрута. Скрипт обнулил счётчик: «0» вместо «3».
- **Причина:** новый атрибут выбран без поиска по коду. Тесты проверяли каждый блок отдельно.
- **Следствие:** ошибку нашёл сам по скриншоту до отправки. Атрибут переименован в `data-count-up`, e2e проверяет оба блока на одной странице.
- **Урок:** перед новым `data-*` атрибутом искать его в `apps/landing/src`. Имя атрибута говорит, чей он.

### №32. `pkill -f` остановил свою же оболочку

- **Что случилось:** в G16 `pkill -f "promo/build.mjs"` остановил сборку ролика и вместе с ней команду, в которой стоял (выход 144).
- **Причина:** `pkill -f` ищет текст во всей строке команды. Текст был и в строке самой оболочки.
- **Следствие:** команда прервалась, изменения после `pkill` не выполнились, пришлось повторить.
- **Урок:** процесс останавливать только по номеру: `ps aux | grep "[b]uild.mjs"`, потом `kill <PID>`.

### №33. Зоны каналов поделил по одному признаку

- **Что случилось:** 30.09 я предложил 4 правки зон только по дорогам, владелец одобрил. Потом владелец попросил проверить население: правки сделали зоны неравными. Разница между самой маленькой и самой большой зоной выросла с 4 раз до 30 раз (Zarafshon, Uchquduq 0,15 млн, Samarqand 4,3 млн).
- **Причина:** правило «одна дорога» проверил, правило «в канале достаточно людей» только записал, но не посчитал.
- **Следствие:** владелец одобрил худший вариант. Пришлось считать заново и просить решение ещё раз.
- **Урок:** решение с несколькими правилами проверять **цифрами по каждому правилу** до того, как просить согласие. Для зон: дорога, расстояние и население из `docs/63`.

### №34. Экраны брали данные только при открытии

- **Что случилось:** владелец увидел, что экраны Mini App не меняются, когда действует другой человек. Водитель подтвердил бронь, а у пассажира статус «Javob kutilmoqda», пока он не закроет и не откроет экран.
- **Причина:** с G07 экраны грузили данные один раз (`useLoad`). Живой канал был только в чате. Тесты проверяли одного человека, не двух.
- **Следствие:** 16 экранов показывали старые данные. Исправлено в G19 (`64`): личный канал, сигнал «изменилось», тихое обновление, обновление при возврате.
- **Урок:** экран с чужими данными проверяется на двух людях: e2e с двумя сторонами или сигналом. Новый экран грузит данные через `useLoad`, тогда он обновляется сам.

### №35. Ответ «Boshqa» оставался на следующем экране

- **Что случилось:** 30.09, пока делал места по модели, тест нашёл ошибку. Водитель вписывал модель через «Boshqa», а следующий экран «Mashina rangi» показывал поле ввода вместо цветов.
- **Причина:** марка, модель, цвет и места показывал один и тот же компонент. React сохранял его состояние «печатаю» между шагами. Тесты шли только по списку, «Boshqa» до конца не проходили.
- **Следствие:** водитель со своей моделью не мог выбрать цвет. Исправлено: у каждого шага свой `key`, экран открывается заново.
- **Урок:** шаги мастера, где один компонент показывает разные вопросы, получают `key` шага. Тест проходит и редкий путь («Boshqa») до конца, не только частый.

### №36. Сигнал шёл, но экран его не слушал

- **Что случилось:** 30.09 аудит (`65`) нашёл: после решения модерации водитель видит «Ariza tekshirilmoqda», пока не откроет Mini App заново. В G19 сервер шлёт сигнал водителю, а экран статуса заявки (`driver-gate.tsx`) его не слушает.
- **Причина:** в G19 я проверял список экранов с `useLoad`, а экраны со своей загрузкой и копии данных при открытии не искал. Написал «сигнал водителю» и не проверил, кто его получает.
- **Следствие:** обещание «экраны обновляются сами» выполнено не везде. Владелец проверил главный сценарий, а этот не проверял.
- **Урок:** для каждого сигнала найти экран, который его слушает, и тест на это. Экран не хранит копию данных при открытии: хранит id и берёт свежие данные из списка.

### №37. Жалоба пропадала, если бронь потом отменили

- **Что случилось:** 30.09 в G20 тест через API нашёл: жалоба на поездку исчезает из очереди команды, если бронь отменили после жалобы. Решение по ней дать нельзя (404).
- **Причина:** с G11 жалоба искала поездку тем же способом, что и подача жалобы: только подтверждённая бронь. Тесты жалоб шли на моках, где бронь не меняется.
- **Следствие:** водитель мог уйти от жалобы отменой брони или удалением аккаунта. Исправлено: у поданной жалобы поездка находится в любом статусе.
- **Урок:** данные, на которые ссылается открытое дело (жалоба, спор), проверяются тестом через API: сначала дело, потом отмена или удаление, потом решение.

### №38. Вид для приложения чуть не ушёл в бота как адрес

- **Что случилось:** в G20 id человека в ответах API стал случайным. Бот уведомлений, напоминания, «Поделиться» и подписки брали id из того же вида и писали бы по нему в Telegram.
- **Причина:** внутренний код брал Telegram ID из вида для приложения. Тип `chatId` принимает и число, и строку, поэтому `tsc` молчал.
- **Следствие:** ошибку нашёл поиском до коммита, сообщения не терялись. Исправлено: бот узнаёт Telegram ID по публичному id.
- **Урок:** вид для приложения только для приложения. Внутренний код берёт id из записи базы. Смена смысла поля: искать всех читателей поля, не только ошибки типов.
