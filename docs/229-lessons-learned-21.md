# 229. Журнал уроков (21)

### №391. Названия областей синие на iPhone

- **Что случилось:** 12.11.2026 владелец прислал снимок с iPhone: на экране «Қаердан йўлга чиқасиз?» названия областей синие, а заголовок и всё вокруг чёрные. Так у попутчика и у водителя.
- **Причина:** плитка области сделана кнопкой, а цвет текста у неё не задан. iOS сам красит слова кнопки в системный синий. Наши снимки и тесты идут в Chromium, где этот цвет чёрный, поэтому разницу не видел никто.
- **Следствие:** разнобой цветов на главном пути выбора места у всех людей с iPhone, пока владелец не заметил.
- **Урок:** у кнопки с текстом цвет задаём сами (`color`), не надеемся на браузер. Снимок экрана выбора области проверяет цвет при синем цвете кнопок, как на iOS.

### №392. Районы шли вразнобой после перехода на кириллицу

- **Что случилось:** 12.11.2026 владелец: «пошёл разнобой» на экранах областей и районов. Районы Хоразма шли так: Боғот, Гурлан, Ҳазорасп, Қўшкўпир, Шовот, Тупроққалъа.
- **Причина:** база сортирует районы по латинскому имени (`ORDER BY … name`), а в G98 мы показали те же имена кириллицей. Порядок латиницы в кириллице выглядит случайным. Тесты проверяли имена, а не порядок.
- **Следствие:** человек дольше ищет свой район. Области не задело: у них свой порядок (`position`).
- **Урок:** когда меняется алфавит показа, меняется и порядок списков. Районы сортирует `byCyrillic` (а … я, ў, қ, ғ, ҳ), а версия справочника меняется, чтобы телефоны загрузили его заново. Снимок экрана районов в тестах показывает порядок.

### №393. CI на main упал на медленном первом показе экрана

- **Что случилось:** 12.11.2026 после слияния #343 CI на main упал: первый тест `live-screens.test.tsx` не уложился в 5 с. На PR он проходил, у меня идёт 0,4 с. Выкладка в прод пропущена.
- **Причина:** первый тест файла рисует тяжёлый экран холодным. На загруженной машине CI это дольше 5 с. Другим тяжёлым экранам уже дали `timeout: 20_000`, этому нет.
- **Следствие:** лишний PR и ещё одно «да» владельца. Перезапустить CI я не могу (403).
- **Урок:** файл тестов, который рисует целый экран, сразу получает `timeout: 20_000` на describe, как `book-flow.test.tsx`.

### №394. Сменил класс плиток, но не во всех тестах

- **Что случилось:** 12.11.2026 в PR #345 я заменил `.direction-card` на `.region-tile` через `sed` по списку файлов, который собрал сам. Два файла снимков (`g59-pixel`, `g75-places-pixel`) в список не попали, CI упал на снимках.
- **Причина:** список файлов я взял из одного `grep` по другой папке и не повторил поиск после замены.
- **Следствие:** лишний круг CI.
- **Урок:** после переименования класса или ключа ищу старое имя по всему репозиторию (`grep -rn` по `e2e` и `packages`), пока поиск не пуст; потом весь проект снимков локально.

### №395. Push в ветку уже слитого PR (повтор урока №300)

- **Что случилось:** 12.11.2026 я добавил коммит «Yordam» и «EP 008» в ветку PR #347. Владелец слил #347 за минуту до моего push. Коммит остался в ветке слитого PR и в main не попал.
- **Причина:** перед push я смотрел только `origin/main` и не прочитал состояние PR. Второй коммит в один PR я делал без проверки, хотя PR уже был зелёный и ждал слияния.
- **Следствие:** перенос коммита на свежий main и новый PR; ещё один круг CI.
- **Урок:** перед каждым push читаю PR (`state` и `merged`). Новую правку в зелёный PR, который ждёт слияния владельцем, не добавляю: делаю отдельный PR.

### №396. Перед push запустил только тесты своего экрана

- **Что случилось:** 12.11.2026 в #348 я поменял темы «Yordam» и запустил только `packages/ui/src/help`. CI упал на `driver-tiles.test.tsx`: тест главного экрана водителя ждал старый порядок тем.
- **Причина:** решил, что изменение касается только экрана «Yordam». Тот же экран открывается и из других тестов.
- **Следствие:** лишний круг CI.
- **Урок:** перед push всегда весь `vitest --project dom` и `--project node` из корня, даже при маленькой правке.

### №397. Коммит прошёл мимо упавшей проверки текстов

- **Что случилось:** 12.11.2026 я закоммитил и отправил `docs/232` с длинным тире «–». `check:text` упал, но коммит в той же команде стоял после `;`, а не внутри условия.
- **Причина:** короткая команда «только docs», правило «коммит только внутри if по кодам выхода» я не применил.
- **Следствие:** в ветку ушёл коммит с запрещённым знаком; лишний коммит с исправлением.
- **Урок:** даже для одной строки docs коммит только после `&&` всех проверок, никогда после `;`.

### №398. Время отправки ботов поменялось, а стенд я гонял только по теме «боты»

- **Что случилось:** 13.11.2026 в G86 правка карточки сразу после прошлой стала ждать свою секунду. Стенд `--area bots` был зелёным, а полный стенд упал на `g88` («поделиться»): сценарий читал карточку бота сразу и видел старые «4 места».
- **Причина:** `g88` живёт в другой теме стенда, но читает карточки ботов. Я считал, что время отправки касается только сценариев ботов.
- **Следствие:** лишний круг полного стенда; сценарий исправлен: ждёт, пока карточка бота совпадёт с карточкой приложения.
- **Урок:** если меняется время или порядок сообщений ботов, сценарии, которые читают сообщения бота сразу после шага, проверять во всех темах (`grep botMessages e2e/stand`), не только `--area bots`.

### №399. Нагрузку ботов (G86 T8) я проверил только на модели

- **Что случилось:** 13.11.2026 тест `load.test.ts` был зелёным: 1000 массовых и 50 ответов без 429. На стенде с лимитом Telegram тот же поток дал 7 … 21 раз 429, ответы до 28 с, а публикация с 1000 подписчиков шла дольше 15 с.
- **Причина:** модель считала очередь и сеть мгновенными. Настоящая очередь отдаёт сообщения пачками, звонки ждут базу и уходят в Telegram разом, длинная задача держит единственного потребителя.
- **Следствие:** три настоящие ошибки нашлись только на стенде; исправлены: ворота темпа в момент звонка в Telegram, новости маршрута задачей очереди частями по 50, один потребитель очереди.
- **Урок:** нагрузку и время проверять на стенде с настоящим Worker и очередью (`/__limit` у Telegram стенда); модель годится только как быстрый тест рядом.

### №400. Выкладка G99 пропущена дважды: фильтр GitHub не видел свежий CI

- **Что случилось:** 13.11.2026 «Deploy production» №101 для G99 дважды решил «ci.yml has not passed»: через 3 секунды и через 10 минут после зелёного CI. Сначала я решил, что GitHub опаздывает на секунды, и добавил повторы; второй пропуск это опроверг.
- **Причина:** запрос `runs?head_sha=…&status=success` для свежего коммита отвечает 0 ещё минуты; без `status` тот же запуск виден сразу с `conclusion: success`.
- **Следствие:** G99 не попала в прод, владелец дважды ждал выкладку.
- **Урок:** проверку внешнего состояния сверять на настоящем API до вывода о причине; фильтры GitHub по статусу не использовать, результат проверять по полям ответа.

### №401. Путь G99: шаги «Qayerdan» и «Qayerga» всегда 0, старые ошибки ушли в «Toʻgʻridan toʻgʻri»

- **Что случилось:** 13.11.2026 на снимках прода «Qayerdan tanladi» и «Qayerga tanladi» показали 0 и «100% ketdi». Все 294 ошибки встали в «Toʻgʻridan toʻgʻri», «Versiyasi nomaʼlum» и «Nomaʼlum ilova».
- **Причина:** путь G99 взял события `way_step` from и to, а экран поиска давно шлёт только opened и done: я не проверил, что событие на самом деле уходит. Ошибки до G99 без метки считались как «без источника».
- **Следствие:** два шага пути попутчика пустые; срезы ошибок врали. Владелец увидел это только на проде.
- **Урок:** каждый шаг воронки проверять тестом экрана: событие уходит. Строки без новых полей не относить ни к какому срезу, их не считать.
