# 91. Журнал уроков: продолжение 6

> **Кратко:** продолжение `26`, `44`, `49`, `66`, `84` (уроки №80 и дальше). Что случилось, причина, следствие, урок. Урок становится правилом.

### №80. Тест нажимал кнопку за день до поездки

- **Что случилось:** «Mashinaga chiqdim» была видна за день до поездки (`89` P7). Три теста UI и e2e нажимали эту кнопку и проходили.
- **Причина:** часы тестов стоят на 1 октября, поездки в тестах на 2 октября. Ошибка продукта была обычным путём тестов, поэтому её никто не видел.
- **Следствие:** кнопки видны только в день поездки по Ташкенту. Тесты нажатия идут утром дня поездки (`TRIP_DAY`), подтверждённая бронь e2e уходит позже сегодня.
- **Урок:** для правила о времени тест проверяет обе стороны границы: «ещё рано» и «уже можно». Данные тестов не должны сами стоять на запретной стороне.

### №81. Находка обхода была уже исправлена

- **Что случилось:** F-P5 (`90`) сказал, что последние места вне зоны уводят карту за границу. Фильтр зоны уже был с G26, но теста на него не было.
- **Причина:** агент обхода читал `recent-list.tsx` без `point-screen.tsx`, где фильтр стоит.
- **Следствие:** код не меняли, добавили тест. Он падает, если фильтр убрать.
- **Урок:** находку обхода сначала проверить по коду. Уже исправленное закрыть тестом, а не второй правкой.

### №82. LIMIT в базе, фильтр после

- **Что случилось:** медиана цен (`90` F-A7) брала 5000 самых старых поездок с даты, потом выбрасывала будущие и отменённые. Список команды (F-A6) так же резал на 200 без слова.
- **Причина:** общий метод `since(from, limit)` отдавал всё подряд, отбор шёл в коде после `LIMIT`.
- **Следствие:** два метода с отбором в SQL: `between` (день команды) и `pricedBetween` (прошлые, не отменённые, свежие первыми), новый индекс `trips_depart`. Мок e2e тоже отдаёт поездки по дню запроса.
- **Урок:** всё, что сужает список, стоит в запросе до `LIMIT`. Лимит только страхует, а не решает, что увидит человек.

### №83. Тест стенда открывал «первую карточку» водителя

- **Что случилось:** после F-D3 сценарий G21 №2 упал: водитель отменил бронь, а экран попутчицы не изменился.
- **Причина:** тест открывал первую карточку с именем водителя. Новый порядок поднял наверх другую бронь Зарины, уже в дороге, из другого сценария. Тест смотрел не на ту бронь.
- **Следствие:** тест открывает нужную бронь по её ссылке (`BOOKING_LINK`), как кнопка бота.
- **Урок:** тест выбирает запись по её id или ссылке, а не по месту в списке. Порядок списка может меняться по делу.

### №84. Имя бренда в тексте продукта

- **Урок:** в текстах на согласие имя бренда сразу писать как `{brand}` и показывать владельцу пример с подстановкой.

### №86. Стенд и e2e в одно время

- **Что случилось:** первый прогон стенда G29 дал 9 падений по таймауту. В те же минуты я запускал e2e для скриншотов.
- **Причина:** стенд и e2e поднимают свои Mini App и браузеры на одной машине. Они мешали друг другу и не успевали ответить.
- **Следствие:** следующие три прогона без e2e рядом: 107 из 107 каждый. Код не менял.
- **Урок:** пока идёт `pnpm stand:check`, ничего другого с браузером и серверами не запускать. Прогон, рядом с которым шёл другой тест, не считается.

### №87. Тест модуля в слое `application` взял код из `infrastructure`

- **Что случилось:** новый тест поддержки (G30) лежал в `support/application` и брал память связей из `infrastructure`. ESLint остановил: слой `application` зависит только внутрь (`11`).
- **Причина:** тест положил рядом с кодом, который он проверяет, а не подумал, какие слои он собирает.
- **Следствие:** тест лежит в корне модуля (`modules/support/support.test.ts`): там можно собрать слои вместе.
- **Урок:** тест, который собирает слои модуля, лежит в корне модуля. Тест внутри слоя берёт только этот слой и слои глубже.

### №88. Кнопка управления командой под обращением человека

- **Что случилось:** под каждым обращением в поддержку владелец видел кнопку «Moderator qilish». Владелец сказал: это неправильно.
- **Причина:** кнопку поставили туда, где был Telegram ID человека. Удобно для кода, но обращение превратилось в место для решений о команде.
- **Следствие:** кнопки под обращением нет. Модератора добавляют командой `/team add <Telegram ID>` (решение владельца).
- **Урок:** обращение человека содержит только его вопрос. Управление командой живёт в своём месте, а не рядом с данными людей.

### №89. Заглушка стала видеть больше, и старый помощник теста сломался

- **Что случилось:** T64 падал на стенде 3 раза подряд. Бот отправил сигнал команде, а тест его не видел.
- **Причина:** заглушка Telegram начала читать получателя у альбомов (для голосовых). Помощник `toldBy` искал сообщение с пустыми словами и брал первый альбом без текста. Второе: заглушка после очистки снова считала номера сообщений с 1, и Reply мог попасть на чужую копию.
- **Следствие:** `toldBy` пропускает сообщения без текста. Номера сообщений в заглушке не повторяются.
- **Урок:** когда заглушка начинает отдавать новые данные, прогнать весь стенд и смотреть падения в старых сценариях. Тест ищет по точному признаку, а не по «первому подходящему».

### №90. Стенд перезапускает Worker после чтения базы извне

- **Что случилось:** сценарий G31 падал с «other side closed», а вручную тот же запрос отвечал за 0,02 с.
- **Причина:** тест читает базу стенда через `wrangler d1 execute`. После этого локальный Worker иногда перезапускается, и запрос в эту секунду обрывается. Для Cron защита уже была, для сообщений ботам не было.
- **Следствие:** `bot-kit` ждёт Worker (`workerBack`) и отправляет сообщение ещё раз, как `runCron`.
- **Урок:** любой запрос теста к стенду после чтения базы проходит через одну защиту от перезапуска. Новую защиту делать общей, а не в одном месте.

### №91. Одной повторной попытки после перезапуска Worker мало

- **Что случилось:** S27 упал на стенде G32 с «other side closed» на втором запросе Cron.
- **Причина:** Worker ответил на проверку здоровья, а потом всё же перезапустился. `runCron` и `bot-kit` пробовали только один раз повторно, и каждый по-своему.
- **Следствие:** одна общая функция `despiteReload` в `stand-tools.ts`: до 3 попыток, между ними ожидание Worker. Её используют Cron и боты.
- **Урок:** защита от перезапуска одна на весь стенд, и в ней несколько попыток. Это продолжение урока №90.

### №92. Прокрутку чинили по одному экрану, и находка вернулась на 20 экранах

- **Что случилось:** обход G33 нашёл ~20 экранов, которые открывались прокрученными, хотя урок №67 уже требовал «каждый экран сверху».
- **Причина:** в G27 исправили только `StepLayout` и `RouteScreen`. Остальные экраны остались без правила, а новые его не получали. Это повтор урока №66.
- **Следствие:** обёртка `Screen` в `packages/ui`: каждый экран объявляет себя ею, она открывает экран сверху и держит «Назад». Все 69 файлов переведены на неё (`94`).
- **Урок:** правило «для всех экранов» делается в одной обёртке, а не исправлением найденных экранов. Если урок звучит «каждый экран …», ищем место, через которое проходят все экраны.

### №93. Подписчик ленты вернул promise, и тест ждал его вечно

- **Что случилось:** после G33 семь тестов главного экрана падали по таймауту: тихое обновление приходило, а экран не перерисовывался.
- **Причина:** `refresh` стал возвращать promise (для свайпа обновления), а лента отдавала его наружу. Тест вызывал сигнал через `act(signal)`, `act` принимал promise за асинхронный и не применял обновления.
- **Следствие:** лента вызывает `() => void refresh()`, ничего не возвращает.
- **Урок:** слушатель события ничего не возвращает (`void`). Promise отдаём только тому, кто его ждёт.

### №94. Коммит ушёл в ветку уже слитого PR, с ним файл сборки

- **Что случилось:** правка оферты (почта) запушена в `docs/g33-close`, когда PR #93 был уже слит и ветка удалена. Push создал ветку заново. В коммит попал `tsconfig.tsbuildinfo`.
- **Причина:** не проверил состояние PR перед push. `tsc -b` пишет файл сборки в корень, а `git add -A` добавил его.
- **Следствие:** правка перенесена в новую ветку от `main` без файла сборки. Лишнюю ветку удаляет владелец.
- **Урок:** перед push в ветку PR проверять, что PR открыт. Типы проверять `pnpm typecheck`, не `tsc -b`. В коммит добавлять файлы по именам, а не `git add -A`.

### №96. Сокет чата на стенде открывался без повтора

- **Что случилось:** в 3-м из 3 прогонов стенда G34 упал сценарий G33 F10 ещё до своего экрана; текст ошибки не сохранился: журнал прогона фильтровался по строкам «✘».
- **Причина:** `writeInChat` открывал WebSocket чата один раз. Запросы сценариев идут через `despiteReload` (урок №91), а сокет нет: перезапуск Worker после чтения базы снаружи рвёт его.
- **Следствие:** сокет открывается до 3 раз с ожиданием Worker (`g33-kit.ts`); прогоны стенда пишутся в журнал целиком.
- **Урок:** любое соединение сценария с Worker (запрос или сокет) идёт с повтором. Журнал прогона сохранять полностью, фильтровать уже после.
