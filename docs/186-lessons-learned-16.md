### №288. Стенд упал на старой сборке бренд-пакета

- **Что случилось:** G81, 15.10.2026: после слияния `main` (G83) полный стенд уронил 2 сценария G83: нет файла `kit/telegram/bot-main-avatar.png`.
- **Причина:** папка `brands/rida/brand-kit/kit` не хранится в git, а моя сборка была до G83. Код был верный.
- **Следствие:** лишний круг стенда; после сборки пакета оба сценария зелёные.
- **Урок:** после слияния `main` с новым ботом или картинкой бренда сначала собираю бренд-пакет (`pnpm --filter @platform/brand-kit-rida build`), потом стенд.

### №289. Имя метода из запроса как ключ обычного объекта

- **Что случилось:** G82, 15.10.2026: CodeQL на PR #238 нашёл серьёзную находку в заглушке стенда `telegram-looks.mjs`: `reads[method]?.(…)`, где `method` берётся из адреса запроса.
- **Причина:** у обычного объекта есть свои методы (`constructor`, `toString`); такое имя вызвало бы чужую функцию. Я не считал заглушку стенда кодом, который читает чужой ввод.
- **Следствие:** вреда нет, это локальный стенд; два лишних круга CI: CodeQL помечает и вызов функции из `Map` по такому имени. Исправлено: имя только сравнивается с известными, тест на оба имени.
- **Урок:** имя из запроса (адрес, тело, заголовок) никогда не выбирает функцию для вызова: только сравнение с известными именами. Данные по такому ключу ищу в `Map`. В любом коде, тестовые заглушки тоже.

### №290. Выкладка без секретов упала с непонятной ошибкой

- **Что случилось:** 15.10.2026, PR #237 слит в `main` раньше шага 1 владельца. `deploy-internal` запустился с пустыми `CLOUDFLARE_API_TOKEN` и `CLOUDFLARE_ACCOUNT_ID` (в Environment `internal` их ещё нет) и упал с ошибкой Cloudflare «Invalid format for Authorization header».
- **Причина:** скрипт выкладки не проверял секреты до первого запроса. По ошибке не видно, что их просто нет.
- **Следствие:** ничего не выложено и не сломано (проверка аккаунта остановила шаг до изменений), но причину пришлось искать по журналу.
- **Урок:** скрипт, которому нужны секреты, сначала проверяет их и называет пустые по имени и место, куда их добавить. Тест на пустые секреты.

### №291. Следующую цель взял из старой копии таблицы целей

- **Что случилось:** 15.10.2026 владелец попросил «дай следующую цель». Я прочитал `docs/goals/INDEX.md` из своей старой ветки и дал G69. В `main` другая сессия уже перенесла запуск на 18.10 и поставила G69 «после запуска».
- **Причина:** перед выбором цели я не обновил `main` (`git fetch`), а читал таблицу из ветки, сделанной до чужих слияний.
- **Следствие:** владелец начал цель, которая по плану идёт после запуска; пришлось спросить отдельно (решил: делать сейчас).
- **Урок:** перед «дай следующую цель» и перед каждой новой веткой: `git fetch origin main` и читаю таблицу из `origin/main`. Если цель стоит «после запуска», говорю: «Это может отдалить запуск».


### №292. В цепочке команд оказался `git checkout -p`

- **Что случилось:** G69, 15.10.2026: я проверял, что тест падает без нового кода. Для этого временно испортил файл, а в той же цепочке команд вызвал `git checkout -p --`, чтобы вернуть его. Эта команда спрашивает про каждый кусок всех изменённых файлов и может отменить чужую работу.
- **Причина:** спешка: я хотел вернуть один файл и взял команду для всех файлов.
- **Следствие:** ничего не потеряно: без ответа команда вышла сама. Я сверил `git status` и файлы: всё на месте.
- **Урок:** файл для проверки «тест падает» сохраняю копией в черновики и возвращаю копированием. `git checkout`, `git restore`, `git reset` в цепочки команд не ставлю никогда; если нужны, то отдельной командой с одним файлом и после `git status`.

### №293. PR ушёл в CI до полной проверки, CI нашёл три ошибки

- **Что случилось:** G69, 15.10.2026: черновик PR #246 упал в CI: тест профиля ждал редакцию политики 1.6, файл стилей стал длиннее 150 строк, а `gitleaks` принял строку `"later": "Keyinroq"` с длинным ключом следующей строки за ключ API.
- **Причина:** я отправил ветку, пока `pnpm check` ещё шёл. Номер редакции искал не во всех папках. `gitleaks` локально не стоит, поэтому его шаг я не видел.
- **Следствие:** CI красный на одном коммите; ложную находку в старом коммите ветки пришлось занести в `.gitleaksignore` (переписать историю ветки нельзя).
- **Урок:** ветку с кодом отправляю только после зелёного `pnpm check` целиком; `gitleaks` скачиваю по SHA-256 из `ci.yml` и запускаю `gitleaks git` до push. Номер редакции и другие общие числа ищу `grep -rn` по всему репозиторию.
